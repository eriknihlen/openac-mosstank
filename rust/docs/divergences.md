# Divergence register: where the Rust conversion deliberately differs

Every deliberate difference from the C# plugin's behaviour. A commit that
adds one adds its row; a commit that removes one deletes the row.

| Id | Where | C# | Rust | Why |
|---|---|---|---|---|
| COMPAT-1 | numbers (SDK kit) | some text uses the current culture | always the invariant culture | the kit's rule; MossTank's own C# formats invariantly almost everywhere |
| COMPAT-2 | numbers (SDK kit) | any format string | format strings the kit does not reproduce are errors | the kit's rule |
| COMPAT-3 | JSON (SDK kit) | indented JSON with the platform's line breaks | `\r\n` | the kit's rule |
| COMPAT-4 | JSON (SDK kit) | lenient readers | a strict reader | the kit's rule |
| COMPAT-5 | regex (SDK kit) | 100 ms match timeout | a backtracking step limit | deterministic on every machine; owner decision (plan question 8) |
| FMT-1 | `.af` reader | an `IF:` at the end of the file throws an index error; a pause or jump charge past the 32-bit range throws an overflow out of `TryLoadNav` | both are refusals (`expected a 'DO:' line.`, a shape error) | a reader never panics on malformed input |
| COMPAT-6 | invariant-culture order (SDK kit `text::collation`; `listsort` without an expression) | ICU's root collation for every character | .NET's order for U+0000–U+024F, General Punctuation and Currency Symbols; any other character sorts after those, by code point | the kit's rule: the full ICU table would add about a megabyte to the plugin |
| EXPR-2 | stopwatches, clocks | the machine's clocks, read directly | the host's clocks through `ExpressionClock` | a plugin reads time only through its host; a test gets a still clock |
| MON-1 | monster spec regex `#` (`mosstank-settings::monster::expression`) | .NET's `RegexParseException` and `RegexMatchTimeoutException` (25 ms) messages | the compatibility kit's messages; its step limit for the timeout | the kit has no .NET message text; the outcome (no match, the error reported) is the same |
| SET-1 | settings profile load and save (`mosstank-settings::profile`) | a row too short for a column it reads (the `Settings` table, the recharge plan), or a missing `Setting`/`Value` column met by `Save`, throws `ArgumentOutOfRangeException`, which the profile store does not catch | a `FormatError` carrying .NET's message, which the store (MT-3) will treat as a failed load | a reader never panics on malformed input |
| STORE-1 | UB settings files (`mosstank-stores::ub_store`) | each tier's file is read on its first use and written on every change | the tiers are read when the store is bound or loaded (the profile tier when a profile is chosen or made); a changed tier is written at `flush`, which the plugin calls before its call returns | the client is reached only during a plugin call, through the storage handed in, and the catalogue reads values without one; the files after a call are the same |
| STORE-2 | JSON a store reads (`mosstank-stores`) | System.Text.Json's `JsonException` text (with path, line and byte position) in the warning | the kit's parse error, or a conversion message naming the JSON path | the kit's reader has its own messages; the outcome (the file is reported and not written over) is the same |
| STORE-3 | paths shown to the player (`mosstank-stores::storage::display_path`) | `Path.Combine` with the platform's separator | the separator of the root the client describes (a backslash for a Windows root) | a WebAssembly plugin has no platform; on Windows the text is the same |
| STORE-4 | global variables' lock (`mosstank-stores::global_variables`) | a machine-wide named mutex, waited for | the client's storage lock, which refuses while another client holds it: that read or write fails as a storage failure | the plugin API's lock does not wait (a plugin call must not block the session); every hold is one file replace, so a refusal is rare and fails only the expression that met it |
| STORE-5 | side-car and old profile documents (`mosstank-stores::sidecar`, `legacy`) | a `null` list or a `null` entry in one (written by hand) throws `NullReferenceException` out of the load; an enum number the C# has no member for is kept as that number | a `null` list reads as empty and a `null` entry is skipped; an unknown number for a consumable kind, loot action or damage type refuses the document, which then reads as missing (the defaults apply, as for any document that will not read) | a load must not panic; the Rust enums hold only their members. MossTank writes neither shape itself |
| AUTO-1 | the cast tracker's callbacks (`mosstank-automation::cast_tracker`) | `ReissueCast`, `SpellAttempted`, `SpellAnswered` and `Completed` run inside `Advance` and `ObserveChat` | they queue as `CastEvent`s the owner drains right after the call, in the same order | re-issuing a cast needs the host, which the owner holds for the call; the casts sent in a frame are the same |
| VIT-1 | vital counts in the recharge (`mosstank-buffs::recharge`, `recharge_controller`) | `checked` conversions of a vital, a missing amount or a transfer estimate past the 32-bit range throw `OverflowException` out of the plan | the value is held at the range's edge | a rule must not panic; the client's vitals never come near that range |
| MANA-1 | worn-gear appraisal lifetimes (`mosstank-buffs::mana`) | an unseeded `Random` draws each worn item's 120–360 s appraisal lifetime | .NET's seeded generator (`DotNetRandom`), seeded by the caller | a WebAssembly plugin has no entropy source of its own; the plugin seeds it from the host clock, so the spread differs from run to run as before |
| META-1 | world objects as text (`mosstank-meta::runtime`) | the name is looked up in the client each time the value is printed | inside an evaluation (tostring, `+`, `==`, `#`, echo, chat output) the client is asked; a value printed outside one (by the caller) uses the name the runtime last read for that id, "(Invalid)" once a read found it gone | the client is reached only during a plugin call, through the host handed to it; every print a meta makes is inside an evaluation |
| META-2 | chat lines a meta submits (`mosstank-meta::engine`, `chatbox[]`) | `IPluginChat.Submit` runs the plugin's own verbs before it returns, so `/vt meta load` replaces the profile mid-pass | the line goes through `MetaServices::submit_chat`, which runs the plugin's own verbs at once and hands back a profile the line loaded; the engine takes it there and then | the SDK runs a submitted plugin verb only after the call returns; the outcome (the load ends the pass) is the same |
| META-3 | the client's notifications (`mosstank-meta::engine`) | the engine subscribes to `IEvents` and unsubscribes in `Dispose` | the plugin calls `on_login_complete`, `on_logoff`, ... from its events; nothing subscribes | a plugin receives events through its `on_event`; `MetaGameEventTests.DisposeUnsubscribesFromTheClient` has nothing to test |
| META-4 | meta views (`mosstank-meta::engine`) | `MetaServices.CreateView`/`DestroyView` (the default refuses every view; the panel wires the view manager) | the engine owns the view manager and always keeps a meta's views | the panel's wiring is the only one the plugin uses; the engine's own functions and the ui* functions reach the views without a back reference |
| META-5 | SetOpt `EnableMeta` (`mosstank-meta::engine`) | the panel's option write starts or stops the engine | the engine starts or stops itself after the services accept the write | the services cannot reach the engine they are called from |
| META-6 | a failed code string with the debug setting on (`mosstank-meta::runtime`) | the whole .NET exception (`ToString`: type, message, stack) | the exception's type name and message | there is no .NET exception; the message is what a reader needs |
| META-7 | `MacroDebugLog.Record` (`mosstank-meta::debug_log`) | stamps `DateTimeOffset.UtcNow` | the caller passes the time | a plugin reads time only through its host |
| META-8 | scheduler hooks (`mosstank-meta::scheduler`) | settable delegates (`MetaPass`, `PassStarting`, `Log`, `LockStateSuffix`) | the methods of `MacroContext`, the plugin's state for the call; "unbound" is `has_meta_pass`/`has_log` answering false | a rule and the scheduler run with the plugin's own state instead of capturing it |
| NAV-1 | the waypoint whose action is worked (`mosstank-nav::controller`) | the action is the waypoint object itself (`ReferenceEquals`), so a list replaced under the controller starts the action afresh | the action is known by its place in the route | the route is the player's settings, handed in for each call; every edit to the route list resets the controller (the panel does so), so the two agree |
| NAV-2 | a chat-command waypoint's line, and the marketplace recall (`mosstank::nav_host`) | `IPluginChat.Submit` answers false when the client took no line, and the waypoint says "Chat command was refused." and tries again | the SDK takes every line (`chat_submit` answers nothing), so the waypoint always completes | the SDK's submit has no refusal to report; the line runs once the plugin's call returns (as META-2) |
| VEND-1 | a vendor profile the storage fails on (`mosstank-vendor::controller`) | a read failure while the tiers are looked through, or while the file is read, throws out of the run's start | the run ends as for a profile that does not read: "Vendor profile could not be read: <file>" as the tool's error, then the finished line | a run must not panic; the profiles that wait on the finished line still see it |
| VEND-2 | the vendor's events (`mosstank-vendor::controller`) | the controller subscribes to `IVendorAutomation.Opened`, `Closed` and `TransactionCompleted` and unsubscribes in `Dispose` | the plugin forwards them (`on_vendor_opened`, `on_vendor_closed`, `on_transaction_completed`); they are drained on the next tick as the C#'s handlers' queue is | a plugin receives events through its `on_event` (as META-3) |
| NAV-3 | the hold on the client's walks (`mosstank::nav_host::GoToPause`) | `PauseGoToWhile(() => panel.WalkPauseReason)`: the client reads the reason whenever it asks | the plugin takes the pause at start and sets its reason on each frame it runs, when the reason changed | the SDK's pause takes a reason, not a callback (plan G1); the reason can trail the macro by one frame |
| LOOT-1 | loot requirement patterns (`mosstank-loot::requirements`) | a VTClassic pattern that runs past .NET's 100 ms match timeout throws `RegexMatchTimeoutException` out of the loot pass | the match is a failure like a pattern that does not compile: the rule does not match, with the reason | a rule must not panic; the kit's step limit stands in for the timeout (COMPAT-5) |
| LOOT-2 | checked conversions in the looter (`mosstank-loot::requirements`, `salvage`, `rules`) | the magical-icon test's `checked((int)Effects)`, the combine planner's `checked((int)material)` and LINQ's checked `Sum` of stack sizes throw `OverflowException` out of the loot pass | effects past the int range read as not magical, a material past it uses the default combine ranges, stack and value sums do not overflow | a rule must not panic; the client's values never come near those ranges |
| LOOT-3 | a corpse answered without a description (`mosstank-loot::host::LootCorpse::from`) | the client's `IsAppraisalAnswered` says a decayed corpse's request came back empty, and it is passed over at once | the SDK's `LootContainer` does not carry that flag, so the plugin reports it as not answered: such a corpse is asked about until its three attempts are spent, then skipped for the blacklist time | an SDK gap; the controller already honours the flag, so it closes when the SDK reports it |
| LOOT-4 | the donor journal's complete-inventory test (`mosstank-loot::host::LootHost::owned_inventory_complete`) | `IsOwnedInventoryComplete` says every pack is listed, so a donor missing from it loses its permission and a held stone missing from it is settled | the SDK has no such flag, so the plugin reports false: a missing donor keeps its (unusable) permission and a held stone settles only when it is seen charged | an SDK gap; false is the side that never sends a destructive use on a guess |
| LOOT-5 | the donor journal file (`mosstank-loot::donors`) | a `null` entry in the list (written by hand) throws `NullReferenceException` out of the load | the file is refused like any other invalid history: draining is disabled and the file is not written over | a load must not panic; MossTank never writes that shape |
| LOOT-6 | MossTank's loot classifier (`mosstank-loot::classifier`) | the stored-profile cache is timed with the machine's clock, and a VTank profile that cannot be read throws out of the classifier | the host's clock, passed in; a profile that cannot be read is not found | a plugin reads time only through its host (EXPR-2); a classifier must not fail the asking plugin's call |
| UB-1 | alias outputs sent on their own (`mosstank-ub::alias::AliasController`) | the chat surface runs the interceptor inside `Submit`, so a flag set while the outputs are sent lets them through untouched | the client carries out a plugin's submitted lines after the call returns; the controller remembers what it sent and lets each through once when it comes back | the outcome (an alias's own output is never aliased again) is the same; a line the player types that is word for word an output still on its way passes once |
| UB-2 | alias patterns (`mosstank-ub::alias`) | any .NET pattern; a match past 100 ms is skipped with a warning | the compatibility kit's patterns: one the kit does not reproduce is refused as a line that does not parse; the step limit stands in for the timeout | the kit's rule (COMPAT-5); the kit covers the patterns aliases are written with |
| NAV-4 | the tight-goal warning and the creep status (`mosstank-nav::controller`, over `mosstank-combat::mover`) | the mover's callbacks post the warning and set the route's status inside the steer, before the gate is asked for magic mode | the shared mover queues both (`take_low_stop_distance_warning`, `take_status`); the route posts and sets them as soon as the steer returns | one mover serves the fight and the route; a chat line the gate itself posts in the same steer comes before the warning instead of after it |
| COMBAT-1 | the gate's callbacks into the fight (`mosstank-combat::gate`) | `CombatModeGate` calls the controller's `AmmunitionStale` and `WieldAmmunition` delegates, and its stop delegate disables the macro, from inside `TryPrepare` | the stale test is a hook handed in with the call; the wield and the stop are requests the gate holds (`take_ammunition_wield`, `take_stop_request`) and the fight takes right after the call | the gate and the fight are separate owners; the requests are taken in the same pass, before anything else is sent |
| COMBAT-2 | equipment placement events (`mosstank-automation::equipment`) | `EquipmentTracker` subscribes to the host's placement event | the tracker drains `take_equipment_observations()` whenever it is read or advanced | a plugin receives nothing between calls; every read sees every placement made before it |
| COMBAT-3 | the cast tracker heard by the fight (`mosstank-combat::controller`) | the tracker's events reach the fight inside the tracker call that raised them | the fight drains the queue (AUTO-1) after each chat line it feeds the tracker and at the top of each turn | a re-send or timeout raised by a frame's `Advance` is heard at the start of the next turn, before the pass decides anything |
| COMBAT-4 | a failed read of the other clients (`mosstank-combat::controller::observe_remote_casts`) | `CaptureClients` can throw, and the batch is read again on the next look (`FailedTrustReadDoesNotConsumeAnEligiblePeerCast`) | the client list read cannot fail | the SDK's read is infallible; that C# test has nothing to test |
| COMBAT-5 | the crafting hook (`mosstank-combat::controller`) | the controller holds the panel's ammunition-crafting planner object | the planner is handed in with each call (`AmmunitionCrafting`), its plans named by opaque handles | the fight does not own the crafting state; the plans it acts on are the same |
| STORE-6 | item enchantment timers (`mosstank-buffs::item_ledger`) | every change is written to the store at once | changes are kept as deferred writes and written at `flush`, before the plugin's call returns | the client's storage is reached only during a call (as STORE-1); the files after a call are the same |
| COMBAT-6 | an equip in flight (`mosstank::automation::HostAutomation::equipment_busy`) | the runtime surface asks the client whether an equip it started is still running | false: the SDK has no such query; the gate still waits on the server's placement before it moves on | an SDK gap; it closes when the SDK reports it |
